# Calculation accuracy and reading relevance roadmap

## Executive finding

The product already has a strong evidence structure: a natal foundation, twenty supported vargas, Vimshottari timing, Ashtakavarga, strength scoring, yogas, transits, and a life-domain synthesis that withholds sensitive divisional and timing claims when the birth time is approximate.

The next gain will not come from adding more charts. It will come from improving the astronomical reference layer, finishing simplified classical calculations, making birth-time uncertainty measurable, and requiring independent confirmation before a client-facing claim is promoted.

## What the engine does today

- The astronomical core uses `astronomy-engine`, even though its source filename retains the older `swiss-ephemeris-engine` name. The UI now reports the actual provider instead of labelling every non-fallback result as Swiss Ephemeris.
- Twenty divisional charts are calculated: D1, D2, D3, D4, D5, D6, D7, D8, D9, D10, D11, D12, D16, D20, D24, D27, D30, D40, D45, and D60.
- The life-domain engine combines natal promise, relevant varga evidence, Shadbala, Ashtakavarga, yogas, dashas, and transits. It already gates fragile conclusions when the recorded time is not exact.
- The current Shadbala is an intentionally simplified relative strength model, not a complete classical Shadbala implementation. Latitude was accepted by the calculator but was not being supplied by either chart-service path; that data-flow gap is fixed in this change.

## Recommended implementation sequence

### P0 — establish a trusted calculation baseline

1. Add a Swiss Ephemeris reference adapter or an offline golden-fixture suite generated by Swiss Ephemeris. Compare every planet, lunar node, ascendant, midheaven, and house cusp across a representative matrix of dates, latitudes, longitudes, ayanamshas, and house systems.
2. Replace the custom "true node" approximation with the ephemeris provider's supported true-node calculation. The current implementation adds the principal nutation terms to the mean node; that is not equivalent to a complete osculating-node solution.
3. Validate sidereal houses against a reference implementation. The current unequal-house code is custom and includes simplified projections. The Swiss Ephemeris documentation specifically provides sidereal house calculation through `swe_houses_ex` and discusses the true-equator/equinox method.
4. Create release-blocking numerical tolerances: planetary longitude, node longitude, ascendant/cusps, nakshatra boundary, dasha start date, and varga sign. Boundary cases should be tested immediately on both sides of each cutoff.

### P1 — make birth-time reliability a calculation, not a label

1. Preserve the user's uncertainty window (for example, ±2, ±5, or ±15 minutes), rather than only `exact/approximate/unknown`.
2. Recalculate the ascendant, houses, D9, D10, D24, D30, and D60 at both ends of that window. Return a stability score and the exact placements that change.
3. Offer event-assisted rectification using dated milestones. Score candidate times by whether domain-specific dashas, vargas, and transits coherently match those events; show a confidence range rather than a false exact minute.
4. Resolve historical time-zone and daylight-saving rules from the date and coordinates, then keep the resolved IANA zone and original civil-time evidence in the calculation audit.

### P1 — complete strength and aspect logic

1. Either rename the current Shadbala output to "relative six-factor strength" or implement full classical Sthana, Dig, Kala, Cheshta, Naisargika, and Drik Bala with auditable subcomponents and classical unit totals.
2. Add Bhava Bala and a varga-weighting measure such as Vimshopaka Bala. These improve relevance by measuring house support and repeated dignity rather than treating every varga placement equally.
3. Separate Western aspects from Jyotish evidence. Implement graha drishti as directed aspects, keep rashi drishti as a separate optional system, use actual longitudinal motion for applying/separating, and document planet-specific strength rules. The current aspect layer mixes Western aspects with a simplified special-aspect pass.
4. Add dispositor chains, functional benefic/malefic status by ascendant, dignity/avastha, combustion exceptions, and explicit contradiction penalties to the evidence matrix.

### P1 — improve timing relevance

1. Replace the Muhurta sunrise/sunset approximation with the provider's rise/set search, including coordinates, refraction assumptions, elevation where available, and the historical time zone.
2. Make forecast instants local and purpose-specific rather than using noon UTC as a universal target-date approximation.
3. Synthesize timing as `natal promise + relevant varga + dasha/antardasha + transit + Ashtakavarga support`. A single transit or generic aspect should not create a major client claim on its own.
4. Add conditional dashas only when their traditional eligibility rules are satisfied. For KP mode, implement actual cuspal star/sub-lords and ruling-planet logic; a KP label should not only change ayanamsha and houses.

### P2 — improve client relevance and calibration

1. Track which evidence produced each sentence and expose a short "why this appears" trail.
2. Add confidence tiers based on independent confirming families, not the sheer number of triggered rules.
3. Detect near-duplicate claims and contradictions before prose generation.
4. Validate outcomes with an anonymized, consent-based feedback set. Measure calibration and usefulness by domain; do not optimize for generic agreement.

## Acceptance criteria for the next engine release

- The reference matrix passes documented angular tolerances and boundary tests.
- Every displayed provider, ayanamsha, node mode, house system, and time-zone decision is truthful and auditable.
- High vargas carry a stability result derived from the user's time window.
- Strength results expose their subcomponents and identify whether they are classical or heuristic.
- A major client claim requires natal promise plus at least two independent confirming evidence families, with contradictions visible.
- The PDF consumes the same evidence objects and confidence labels as the web report, so the two products cannot drift.
